# Как собираются и ставятся сборки Relay

Коротко и на пальцах: что происходит, когда вы говорите `flutter build`, что
получается на выходе, и что с этим делать дальше — на macOS и на Windows.

---

## 1. Что вообще такое «сборка» Flutter-приложения на десктопе

Flutter-приложение на десктопе — это **обычное нативное приложение**, внутрь
которого положены две вещи:

1. **Нативная оболочка.** На macOS это Xcode-проект в `macos/`, на Windows —
   CMake-проект в `windows/`. Он создаёт окно, запускает движок Flutter и
   подключает плагины. У Relay в этой оболочке живёт почти всё интересное:
   захват экрана, камера, звук, кодирование (`packages/recorder_macos/`,
   `packages/recorder_windows/`).
2. **Ваш Dart-код** — весь `lib/` — скомпилированный и положенный внутрь как
   ресурс.

Поэтому сборка всегда идёт в два шага, и `flutter build` делает оба за вас:

```text
flutter build macos
   │
   ├─ 1. компилирует Dart из lib/  →  App.framework
   └─ 2. запускает Xcode (xcodebuild) по проекту macos/  →  relay.app
```

Отсюда следует главное практическое правило: **`flutter build` — это не «одна
команда», а обёртка над нативным тулчейном.** Нет Xcode — нет сборки под macOS.
Нет Visual Studio — нет сборки под Windows. И собрать Windows-версию с Mac
нельзя: кросс-компиляции у Flutter на десктопе нет, каждую платформу собирают
на ней самой.

### Debug и Release — в чём разница

| | Debug | Release |
|---|---|---|
| Dart | JIT, с проверками | AOT, оптимизированный |
| Скорость | заметно медленнее | боевая |
| Размер | больше | меньше |
| Отладка | есть VM Service, hot reload | нет |
| Для чего | разработка | то, что отдают людям |

Для замеров производительности (сколько кадров теряется, как греется машина)
`--debug` не годится совсем — только `--release` или `--profile`.

## 2. macOS

### Собрать и запустить

```bash
flutter pub get
flutter build macos --release
open build/macos/Build/Products/Release/relay.app
```

Результат — папка `relay.app`. Это и есть «приложение»: bundle, внутри
`Contents/MacOS/relay` (исполняемый файл), `Contents/Frameworks/` (движок
Flutter и плагины), `Contents/Resources/`, `Contents/Info.plist`.

Поставить к себе в `/Applications` — отдельным скриптом, он делает это
безопасно (копия → проверка подписи → подмена, а не `cp` поверх):

```bash
./tool/install.sh --release --build
```

### Запускать только через `open`

```bash
open /Applications/relay.app     # правильно
./relay.app/Contents/MacOS/relay # неправильно
```

macOS приписывает запрос на запись экрана **ответственному процессу**. Если
бинарник запущен из терминала, ответственным считается терминал — а у него
разрешения нет, и Relay не увидит ни одного экрана. Через `open` ответственным
становится само приложение.

### Три вещи, специфичные именно для Relay

**Подпись.** Настраивается в `macos/Runner/Configs/Signing.xcconfig`. Сейчас
там `Apple Development` — этого достаточно, чтобы собирать и запускать у себя.
Своя машина, свои сертификаты — можно переопределить в git-ignored файле
`Signing.local.xcconfig` рядом. Совсем без Apple-аккаунта тоже работает:
`CODE_SIGN_IDENTITY = -`.

**Разрешение на запись экрана.** Даётся один раз в System Settings → Privacy &
Security → Screen & System Audio Recording, **и после этого приложение надо
перезапустить** — macOS применяет это разрешение только при следующем старте.
Если разрешение вдруг «есть, но не работает», **сначала проверь, как приложение
запущено**: бинарник, запущенный из терминала (или `flutter run`), macOS
приписывает терминалу, а не приложению. Это и есть обычная причина.

`./tool/reset-permissions.sh` нужен только для ad-hoc сборки — у подписанной
сертификатом он удаляет рабочее разрешение. См.
`docs/development/macos-tcc-and-launchservices.md`.

Микрофон и камера устроены иначе: если их не разрешить, запись всё равно
пойдёт — просто без этой дорожки.

**Песочница выключена.** Намеренно: записи пишутся в `~/Movies/Relay`, то есть
в обычную пользовательскую папку. В песочнице они попали бы в контейнер
приложения. Для App Store это пришлось бы менять
(`docs/development/compatibility-matrix.md`).

### Где что лежит после установки

| Что | Где | Переживает переустановку |
|---|---|---|
| Само приложение | `/Applications/relay.app` | заменяется |
| Записи | `~/Movies/Relay` | да |
| Настройки | `~/Library/Application Support/com.relay.relay/settings.json` | да |
| Пароли назначений | Связка ключей (Keychain) | да |

## 3. Windows

> **Важно:** на Windows этот проект **ни разу не собирался** — на машине
> разработки нет MSVC. Код написан (`packages/recorder_windows/`, ~9 600 строк
> C++), но не скомпилирован и не проверен. Ниже — как это устроено, а не отчёт
> о том, что оно работает.

### Что нужно на машине

- Windows 10 (сборка 19041) или новее;
- **Visual Studio 2022** с рабочей нагрузкой *Desktop development with C++*
  (именно она, не одна Visual Studio Code);
- Flutter 3.47.1.

Проверить, что Flutter всё видит:

```bash
flutter doctor
```

### Запустить и собрать

На самой Windows-машине всё ровно так же, как на маке — никакой разницы:

```bash
flutter run -d windows
```

```bash
flutter build windows --release
```

Результат — **папка**, а не один файл:

```text
build\windows\x64\runner\Release\
├─ relay.exe            ← запускается вот это
├─ flutter_windows.dll  ← движок
├─ *.dll                ← плагины
└─ data\                ← ваш Dart-код и ресурсы
```

### А если Windows-машины нет

С мака собрать под Windows **нельзя**: кросс-компиляции у Flutter на десктопе
нет, `flutter build windows` работает только на Windows. Варианты, по
возрастанию усилий:

| Как | Что даёт | Чего не даёт |
|---|---|---|
| **GitHub Actions**, раннер `windows-2022` | компилирует все 9 600 строк C++ и отдаёт полный список ошибок и предупреждений | не запускает GUI: проверить саму запись нельзя |
| **Виртуалка**: Parallels / UTM / VMware | собирает и запускает, `flutter run -d windows` работает | захват экрана в виртуальном GPU — не та проверка, которая что-то доказывает про рекордер |
| **Живая Windows-машина** | единственный честный способ проверить рекордер | нужна машина |
| **Облачная Windows с GPU** (Azure, Paperspace, Shadow) | то же самое, посуточно | платно |

**Начинать надо с первого.** В репозитории уже есть workflow
[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) с job `build-windows`,
который делает ровно `flutter build windows`. Он ни разу не запускался —
проект не в git. Довести код до GitHub и один раз прогнать этот job — самый
дешёвый способ узнать, компилируется ли Windows-часть вообще; ничего
устанавливать не нужно.

На Apple Silicon в виртуалке ставится Windows 11 ARM. Visual Studio 2022 там
есть в ARM64-версии, и Flutter умеет `--target-platform windows-arm64`; x64
тоже поедет, через эмуляцию, просто медленнее.

### Почему папка, а не один файл

На macOS `.app` — это одна самодостаточная папка, которую можно просто
перетащить. На Windows такого контейнера в системе нет, и `relay.exe` — это
тонкий запускальщик, которому обязательно нужны соседи:

| Файл | Что это | Почему нельзя вшить внутрь |
|---|---|---|
| `flutter_windows.dll` | сам движок Flutter | Flutter поставляет движок **только** как готовую DLL. Статической библиотеки для Windows не существует — линковать нечего |
| `data\icudtl.dat` | таблицы ICU (Unicode, локали) | движок открывает файл по пути рядом с exe и отображает его в память |
| `data\app.so` | ваш Dart-код, скомпилированный AOT | грузится как отдельный модуль по пути |
| `data\flutter_assets\` | шрифты Barlow, иконки, ресурсы | читаются по путям из `AssetManifest` |
| `*.dll` плагинов | нативная часть каждого плагина | каждый плагин — своя DLL |

Так что «скопировать один `.exe` и отправить» — не выйдет: он запустится и
сразу упадёт, не найдя движок.

### А одним файлом всё-таки можно?

**Отправить одним файлом — да.** Сделать так, чтобы *сам* `relay.exe` был
самодостаточным — нет, Flutter этого не умеет. Разница важная: одним файлом
становится не приложение, а его **упаковка**.

Три рабочих варианта, по возрастанию усилий:

1. **ZIP всей папки `Release\`.** Ноль работы. Получатель распаковывает и
   запускает `relay.exe`. SmartScreen поругается на неизвестного издателя —
   «Подробнее» → «Выполнить в любом случае».
2. **Установщик: Inno Setup, NSIS или WiX.** На выходе один `setup.exe`,
   который распаковывает всё в `Program Files`, кладёт ярлык в меню «Пуск» и
   добавляет запись в «Установка и удаление программ». Это то, как выглядят
   почти все «однофайловые» программы на Windows — включая Chrome, VS Code и
   любое Electron-приложение: внутри у них ровно такая же папка.
3. **MSIX** (пакет `msix` из pub). На выходе один `.msix`, ставится как
   приложение из Store, умеет обновляться и чисто удаляться. Нужен сертификат
   для подписи — самоподписанный тоже сгодится, если получатель поставит его
   в доверенные.

Есть ещё **самораспаковывающийся архив** (7-Zip SFX): один exe, который
распаковывается во временную папку и запускается. Формально «один файл», но
старт медленнее, а антивирусы такое не любят. Для рассылки коллегам — годится,
для чего-то серьёзнее — лучше установщик.

Отдельно про подпись: чтобы SmartScreen молчал, нужен сертификат Authenticode
(OV или EV). Это платно и по смыслу — тот же сюжет, что Developer ID на macOS.
В проекте ни установщик, ни подпись пока не настроены.

Разрешений в стиле macOS на Windows нет: захват экрана не спрашивает ничего,
микрофон и камера управляются в *Параметры → Конфиденциальность*.

## 4. Как отправить сборку другому человеку (macOS, DMG)

```bash
./tool/package-dmg.sh --build
```

Получится `build/relay-<версия>.dmg` — окно с иконкой приложения и стрелкой на
`Applications`.

Но есть нюанс, и он важный. **DMG — это просто коробка.** Откроется приложение
у другого человека или нет, решает подпись внутри него:

| Подпись | Что увидит получатель |
|---|---|
| Apple Development (сейчас) | «Приложение повреждено» / «не удаётся проверить разработчика» |
| Developer ID без нотаризации | то же самое |
| **Developer ID + нотаризация** | открывается двойным кликом, без вопросов |

Сейчас в проекте только сертификаты **Apple Development** — значит, DMG уже
можно собрать и отдать, но получателю придётся один раз выполнить:

```bash
xattr -dr com.apple.quarantine /Applications/relay.app
```

Для нормальной отправки нужен платный Apple Developer Program (99 $/год) →
сертификат **Developer ID Application** → и тогда:

```bash
# один раз: сохранить учётные данные для нотаризации
xcrun notarytool store-credentials relay-notary \
  --apple-id you@example.com --team-id TEAMID --password <app-specific-password>

# каждый раз
./tool/package-dmg.sh --build \
  --sign "Developer ID Application: Ваше Имя (TEAMID)" \
  --notarize relay-notary
```

Скрипт подпишет приложение с hardened runtime, соберёт DMG, отправит его
Apple, дождётся ответа и «пришьёт» тикет к образу (`stapler`), чтобы у
получателя всё работало даже без интернета.

Отдельно про запись экрана: macOS привязывает разрешение к *designated
requirement* подписи, а не к самому коду. И у **Developer ID**, и у
**Apple Development** это требование описывает bundle id и сертификат, поэтому
пересборка с тем же сертификатом разрешение **не теряет** — человек разрешит
запись экрана один раз, и обновления это не сломают.

Теряется оно только при ad-hoc подписи (`CODE_SIGN_IDENTITY = -`): там
requirement — это `cdhash`, который меняется при каждой сборке. Проверить:
`codesign -d -r- <app>`. Подробно — `docs/development/macos-tcc-and-launchservices.md`.

## 5. Шпаргалка

```bash
# проверить, что всё зелёное
./tool/validate.sh

# разработка
flutter run -d macos

# боевая сборка + установка к себе
./tool/install.sh --release --build

# DMG для отправки
./tool/package-dmg.sh --build

# Windows (только на Windows-машине)
flutter build windows --release
```
