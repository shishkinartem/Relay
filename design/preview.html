00Screen Recorder — MVP screen set

Assumptions

Single 420px utility panel, macOS chrome, on the Industry wireframe system — every surface is a square hairline object with registration marks, one steel accent, Barlow Condensed over Barlow. Sized and structured so a Flutter build maps cleanly: each screen is one route or one dialog, each control is a stock widget (SegmentedButton, Radio, LinearProgressIndicator, ListTile).

Panel never grows past 420 × 560. Everything that must sit over other apps — the control strip, the camera preview — is a separate always-on-top window, never a child of the panel, and explicitly excluded from capture. Exclusion is mandatory: with entire screen as the default source, both surfaces sit inside the captured bounds and only excludingWindows: / WDA_EXCLUDEFROMCAPTURE keeps them out of the file.

Screens are annotated with their state from §19 and the spec section they answer. Three open decisions (§30.1, §30.2, §30.5) are shown as concrete proposals, marked TBD.

Camera preview
The strip and the camera preview are separate always-on-top windows, and both must be explicitly excluded from capture — SCContentFilter(display:excludingWindows:) / WDA_EXCLUDEFROMCAPTURE. In window mode the filter already scopes them out; in entire-screen mode, now the default, they sit inside the captured bounds and exclusion is the only thing keeping them out of the file (§6). Placement above the source is presentation, never the mechanism. The preview shows the same logical camera source the compositor draws into the PiP; it is not screen-captured.

One camera surface, not two. In display mode the preview window is placed exactly where the compositor draws the PiP — same size, same corner — so what the user sees on screen is what lands in the file. It carries no labels of its own: it sits over the user's screen and must read as the camera, not as a diagram. It is still an excluded window, so it is not captured; the frames in the file come from the compositor. Window mode (1e) is the case that needs a preview somewhere else, because the PiP position is inside a window the user is not looking at.

04Settings and system states
1mSettings — destination and storage only, §15
Settings
Upload destination
a.petrov@example.com · drive.file scope
Hosted Bot API — long recordings will fail preflight
Entry points: Change beside Send to in 1c, and the gear in its titlebar — the same panel window pushed as a second route, so there is no second window to manage. Quality, frame rate and cursor are not repeated here: they are per-session choices made in 1c, which persists its last values. Settings holds only what outlives a session — destination, account, storage. One active destination per Send (§15). Each destination row surfaces its own UploadCapabilities — the 50 MB tag is read from the destination, not hard-coded in the settings screen, so a Local Bot API URL removes it.
